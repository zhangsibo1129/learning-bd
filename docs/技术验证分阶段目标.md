# 企业本体平台 技术验证 Demo — 分阶段目标

> 定位：这是一份**技术验证（PoC）路线图**，不是生产交付计划。核心目的不是把组件都跑起来，而是验证"一条数据如何从业务系统走到本体对象，并支撑查询、分析、权限、Action 与 AI Agent"。

---

## 一、验证目标

以**制造企业设备管理平台**为唯一主线场景，端到端验证以下能力可行：

- 多源数据（PostgreSQL / CSV / 模拟 IoT）接入平台
- 批流一体处理并落入 Iceberg 数据湖（存储于 RustFS）
- 普通数据被建模为具有业务语义的**本体对象与关系**
- 通过统一 Ontology API 完成对象查询、关系查询、分析、搜索
- 对象级 / 属性级 / Action 级权限可控可验
- Agent 通过本体工具（而非裸 SQL）完成查询与业务操作

**一句话验收标准**：不直接访问底层数据库，也能通过统一本体接口完成"查设备 → 分析状态 → 建维修工单 → 追溯数据来源"的完整闭环。

---

## 二、验证原则

| 原则 | 含义 |
| --- | --- |
| 场景驱动 | 每个组件都必须回答"它在这个业务场景里解决什么问题"，不为学组件而部署组件 |
| 分阶段推进 | 先跑通数据，再理解组件，再构建本体，最后验证企业级能力 |
| 可观测、可验收 | 每个阶段都必须有可运行的代码、可见的数据流、明确的验收判据 |
| Notebook 即验收 | 验收过程写成可执行 Notebook，单步可跑、结果可看、断言可回归，而非截图或口头记录 |
| 单机优先 | macOS + Docker Compose 单机部署，不上 Kubernetes / Helm / 多节点高可用 |
| 留痕 | 每个阶段产出三件套：可运行代码与配置、一张数据流转图、一份验收 Notebook（导出 HTML 存档） |

**反模式**：一开始就把 RustFS、Iceberg、Kafka、Flink、SeaTunnel、PostgreSQL、OpenSearch、StarRocks、OpenFGA 全部拉起——容器全绿，但说不清数据怎么流动、组件为何存在。

## 三、目标架构与组件职责

```
数据源               传输              处理 / 存储              服务化                   本体平台
PostgreSQL  ──┐                  ┌─ Flink ── Iceberg ── RustFS ─┐
CSV         ──┼─ SeaTunnel ── Kafka ─┘        (Catalog)        ├─ StarRocks  (分析)
模拟 IoT    ──┘                                              ├─ OpenSearch (搜索)
                                                             └─ Go Ontology Runtime
                                                                  ├─ Schema Registry
                                                                  ├─ Object / Query Runtime
                                                                  ├─ Action Runtime
                                                                  ├─ OpenFGA (权限)
                                                                  ├─ Lineage  (血缘)
                                                                  └─ Agent Tools
```

| 层次 | 组件 | 唯一职责 | 不该被误解为 |
| --- | --- | --- | --- |
| 业务库 | PostgreSQL | 业务原始数据 + 对象编辑账本 + Schema 元数据 | 分析引擎 |
| 对象存储 | RustFS | 保存 Parquet 等实际数据文件 | 表管理器 |
| 消息总线 | Kafka | 实时事件传输、削峰解耦 | 数据存储 |
| 数据集成 | SeaTunnel | Source → Transform → Sink 的数据搬运 | 计算引擎 |
| 计算 | Flink | 清洗、转换、聚合、事件时间处理 | 存储 |
| 表格式 | Iceberg | 表、Snapshot、Manifest、Schema Evolution | 文件存储 |
| 元数据 | Iceberg Catalog | 表名、表定义、表位置 | 数据文件存储 |
| 分析 | StarRocks | 外部 Catalog 查询、JOIN、聚合（OLAP） | OLTP 替代品 |
| 检索 | OpenSearch | 全文检索、字段过滤、索引服务 | 权威数据源 |
| 本体 | Go Runtime + PostgreSQL | 统一对象模型、查询、Action、权限执行点 | 单纯 ORM |
| 授权 | OpenFGA | 关系型授权判定 | 业务逻辑 |
| 智能 | Agent | 理解本体、选择工具、受权限约束地执行 | 直连数据库的 SQL Bot |

## 四、验证的承载方式：Notebook 交互式

每个阶段的"验收判据"都由一份可执行 Notebook 承载，而不是静态截图、手工命令记录或只写结论的文档。

**统一约定**

- 位置：`notebooks/phase-<NN>-<topic>.ipynb`，与本阶段代码同仓。
- 单元格固定六段结构：

  | 顺序 | 段落 | 内容 |
  | --- | --- | --- |
  | ① | 验证命题 | Markdown 说明"这份 Notebook 证明什么、不证明什么" |
  | ② | 前置检查 | 容器健康、端口连通、依赖版本，任一不满足直接失败 |
  | ③ | 分步执行 | 一步一 cell，可单独运行并观察中间结果（查询结果、消息体、文件列表） |
  | ④ | 断言 | 用 `assert` 校验数量、结构、幂等性与一致性，而不是靠肉眼判断 |
  | ⑤ | 可视化 | 表格、时序曲线、消息流、Agent tool trace 等直观呈现 |
  | ⑥ | 结论 | 记录通过项、异常项、遗留问题与下阶段依赖 |

- 所有 cell 必须能"Restart & Run All"一次跑通；用 papermill 参数化执行作为阶段回归。
- 执行结果导出 HTML 归档到 `docs/acceptance/`，即该阶段的验收记录。

**阶段与 Notebook 对应关系**

| 阶段 | Notebook | 交互内容 | 关键断言 |
| --- | --- | --- | --- |
| 0 | `phase-00-foundation.ipynb` | Docker 检查、psql 建表插数、Python 生成设备数据 | 容器 healthy；表行数等于生成条数 |
| 1 | `phase-01-infra.ipynb` | RustFS 上传/下载、PG 查询、Kafka 生产与消费 | 文件往返内容一致；消息可原样取回 |
| 2 | `phase-02-ingestion.ipynb` | 启动 SeaTunnel 任务、消费 Topic、观察 offset 增长 | 新插入 PG 的行在预期时间内出现在 Kafka |
| 3 | `phase-03-lakehouse.ipynb` | 提交 Flink 任务、列 Iceberg Snapshot、读 Parquet | Snapshot 数量递增；异常温度记录被过滤 |
| 4 | `phase-04-analytics.ipynb` | StarRocks 三组分析 SQL 与结果对比 | 结果集与手算口径一致 |
| 5 | `phase-05-search.ipynb` | 建索引、全文检索、条件过滤、重建索引 | Top1 命中正确；重建后结果与首次一致 |
| 6 | `phase-06-ontology.ipynb` | 查 Schema、调对象接口、一跳关系遍历 | 返回契约字段齐全；关联对象指向正确 |
| 7 | `phase-07-security-lineage.ipynb` | 切换 Alice / Bob 身份请求、查属性血缘 | 敏感字段可见性有差异；血缘链完整可追溯 |
| 8 | `phase-08-action.ipynb` | 执行 Action、重复提交验幂等、查编辑账本 | 重放只产生一条业务结果；审计链完整 |
| 9 | `phase-09-agent.ipynb` | 自然语言请求、打印 tool 调用轨迹 | 工具序列符合预期；权限内工单创建成功 |

## 五、分阶段目标

### 阶段 0 · 基础环境与 Docker

- **验证命题**：是否具备后续所有组件的运行与调试基础。
- **建设内容**：Docker 镜像/容器/网络/Volume/Compose；SQL 与 PostgreSQL；Python 数据生成；HTTP/JSON/Git 基础。
- **验收判据**
  - 用 Compose 启动一个 PostgreSQL；
  - 连库建表、插入、查询成功；
  - Python 脚本能生成模拟设备数据。
- **Notebook 验证**：`notebooks/phase-00-foundation.ipynb` —— 环境自检 → 用 Compose 启 PG → 建表写入 → 查询；断言容器 healthy、写入行数与查询结果一致。

### 阶段 1 · 基础设施三件套

- **验证命题**：数据"能存、能查、能传"。
- **建设内容**：RustFS（Bucket、上传下载）、PostgreSQL（`equipment` / `work_order` 表）、Kafka（Topic 创建、生产与消费）、统一 Compose 编排。
- **验收判据**
  - RustFS 可上传/下载文件；
  - PG 中设备与工单表可用；
  - Kafka 能发送并消费一条消息；
  - 三者一条命令全部拉起。
- **Notebook 验证**：`notebooks/phase-01-infra.ipynb` —— RustFS 上传后下载并比对哈希、PG 查询、Kafka 生产与消费；断言文件往返一致、消息原样取回、容器 healthy。

### 阶段 2 · 数据采集与实时传输

- **验证命题**：企业数据如何自动进入平台，以及重复/丢失如何应对。
- **建设内容**：SeaTunnel 读取 PostgreSQL → 写入 Kafka `equipment-events`；编写消费者；模拟设备状态持续变化。
- **需理解**：Connector、Source/Sink、批 vs 流、Topic/Partition/Consumer Group、投递语义。
- **验收判据**
  - PG 数据经 SeaTunnel 自动进入 Kafka；
  - 可在消费者侧看到消息内容；
  - 设备状态变化能被持续捕获。
- **Notebook 验证**：`notebooks/phase-02-ingestion.ipynb` —— 启动 SeaTunnel 任务、在 PG 更新设备状态、消费 Topic；断言新行在预期时间内到达 Kafka、字段映射正确、无重复消息。

### 阶段 3 · 实时计算与数据湖（第一个技术里程碑）

- **验证命题**：Kafka → Flink → Iceberg → RustFS 的湖仓写入链路是否成立。
- **建设内容**：Flink 消费 Kafka、清洗（如过滤异常温度）、写 Iceberg；独立 Iceberg Catalog；Parquet 格式，几万条数据即可。
- **验收判据**
  - RustFS 中出现 Iceberg 数据文件；
  - 可查询 Iceberg 表、可查看 Snapshot；
  - 新数据到达后表内容可见更新；
  - 能讲清一条数据从 Kafka 到 Iceberg 的完整路径（含 Catalog 的作用）。
- **Notebook 验证**：`notebooks/phase-03-lakehouse.ipynb` —— 提交 Flink 任务 → 查 Iceberg 表 → 列出 Snapshot → 直接读 Parquet；断言 Snapshot 递增、异常温度被过滤、新数据可见、文件确实落在 RustFS。

### 阶段 4 · 分析查询引擎

- **验证命题**：数据湖能否支撑高效 OLAP 分析，而不污染 OLTP 库。
- **建设内容**：StarRocks 外部 Catalog 挂载 Iceberg；实现设备数量、故障率、24h 平均温度、工厂运行情况等分析 API。
- **需理解**：OLTP vs OLAP、行存 vs 列存、外部表 vs 内部表、JOIN/聚合。
- **验收判据**
  - 统计各工厂设备数量；
  - 统计设备过去 24 小时平均温度；
  - 关联设备-工厂-工单，找出故障设备对应的未完成工单。
- **Notebook 验证**：`notebooks/phase-04-analytics.ipynb` —— 三组分析 SQL 逐一执行并展示结果表；断言设备总数、24h 均温口径、故障设备未完工单数与预期一致。

### 阶段 5 · 搜索与索引

- **验证命题**：为什么平台需要独立搜索引擎，以及索引为何不等于数据源。
- **建设内容**：PG/Iceberg → 同步程序 → OpenSearch → 搜索 API；设备名称/型号全文检索、状态与工厂过滤、设备文档检索（向量检索后置）。
- **验收判据**
  - 按设备名称检索到设备；
  - 按故障描述找到相关设备与文档；
  - 索引可重建，权威数据仍在数据模型中。
- **Notebook 验证**：`notebooks/phase-05-search.ipynb` —— 建索引 → 名称检索 → 状态/工厂过滤 → 删除并重建索引后重跑；断言 Top1 命中、过滤结果精确、重建前后查询结果一致。

### 阶段 6 · 本体模型与对象运行时（核心阶段）

- **验证命题**：数据能否升维为带业务语义的对象与关系，并通过统一接口访问。
- **建模内容**

  | ObjectType | 关键属性 |
  | --- | --- |
  | Factory | id、name、location |
  | Equipment | id、name、status、temperature |
  | WorkOrder | id、status、priority |

  | LinkType | 起点 → 终点 |
  | --- | --- |
  | BELONGS_TO | Equipment → Factory |
  | HAS_WORK_ORDER | Equipment → WorkOrder |

- **建设顺序**
  1. Schema Registry（ObjectType / Property / LinkType / ActionType / Schema Version，先存 PostgreSQL）；
  2. Object Runtime（取对象、取属性、取关系、按 ID 取关联对象）；
  3. Query Runtime（如 `GET /api/objects/Equipment/EQ-001`）；
  4. 物理存储映射（对象属性 → PG / Iceberg / OpenSearch 的映射表）。
- **边界**：第一版只支持单对象查询 + 一跳关系，不做复杂图查询。
- **验收判据**
  - 不直接操作底层库，通过本体 API 拿到设备及其关系；
  - 返回结构为 `{id, type, name, status, temperature}` 这类稳定对象契约。
- **Notebook 验证**：`notebooks/phase-06-ontology.ipynb` —— 读 Schema Registry → 调 `GET /api/objects/Equipment/EQ-001` → 遍历 BELONGS_TO / HAS_WORK_ORDER；断言返回字段齐全、关系指向正确、整个 Notebook 未出现直连库的 SQL。

### 阶段 7 · 权限与数据血缘（企业级能力起点）

- **验证命题**：同一对象在不同身份下能否看到不同数据；属性能否追溯来源。
- **A. 权限（OpenFGA）**：Alice（设备维护，仅自己负责的设备）、Bob（设备管理，全部设备）、管理员（可改状态）。
  - 验证层级：对象权限 → 行权限 → 属性权限（成本、供应商等敏感字段）→ Action 权限。
  - 执行分工：OpenFGA 判定授权关系，Go Runtime 强制执行。
- **B. 血缘（Property Lineage）**：`IoT Sensor → Kafka Topic → Flink Transformation → Iceberg Snapshot → Equipment.temperature`。
  - 能回答：数据源是谁、原始数据是什么、经过哪些计算、用了哪个 Snapshot、最后更新时间。
  - 边界：第一版只做 Dataset Lineage + Property Lineage，不建完整血缘图谱。
- **验收判据**
  - Alice 与 Bob 访问同一对象得到不同权限范围的数据；
  - 任一对象属性可回溯到原始数据来源。
- **Notebook 验证**：`notebooks/phase-07-security-lineage.ipynb` —— 用 Alice / Bob / 管理员三种身份请求同一对象、查 `Equipment.temperature` 血缘；断言敏感属性与可见范围存在差异、血缘可回溯到 Topic 与 Snapshot。

### 阶段 8 · Action 与业务闭环

- **验证命题**：平台能否安全地修改业务状态，而不仅是读。
- **业务链路**：发现温度异常 → 创建维修工单 → 设备置为 `MAINTENANCE` → 记录操作人/时间/原因 → 写审计事件 → 触发后续流程。
- **建设内容**（PostgreSQL 版 Transactional Edit Ledger）

  | 表 | 职责 |
  | --- | --- |
  | ontology_object_edits | 对象当前编辑状态 |
  | ontology_edit_events | 不可变编辑历史 |
  | ontology_outbox | 待发布事件 |
  | ontology_actions | Action 执行状态 |

- **验证要点**：版本控制与乐观锁、幂等性、事务提交、Outbox 发布、失败重试、审计与补偿。
- **边界**：不做跨系统分布式事务；先保证 PG 内原子提交，再经 Kafka 异步通知。
- **验收判据**
  - 通过统一 Action API 创建维修工单；
  - 完整操作历史可追踪、可审计。
- **Notebook 验证**：`notebooks/phase-08-action.ipynb` —— 执行创建工单 Action → 相同幂等键重放 → 查编辑账本与 outbox；断言重放不产生第二条业务结果、事件已写入 outbox、审计链完整。

### 阶段 9 · AI Agent 集成与端到端验证

- **验证命题**：Agent 是否真正"用本体"，而不是绕过平台写 SQL。
- **典型请求**："查询生产线一号所有温度异常的设备，分析原因，并为需要维修的设备创建工单。"
- **执行链路**：自然语言 → Agent（任务理解/工具选择/执行计划）→ Ontology Tools（Search / Get / Traverse Links / Execute Action）→ Runtime（Query Planner / Permission / Object / Action）→ 数据执行层（PG / StarRocks / OpenSearch / Kafka）。
- **关键考察点**：是否理解对象与属性语义、是否走关系查询、是否受权限约束、Action 是否安全可审计、执行轨迹是否留痕。
- **验收判据**
  - Agent 通过 Ontology Tools 查到设备并分析状态；
  - 在权限允许范围内成功创建维修工单；
  - 全过程有可回放的工具调用轨迹。
- **Notebook 验证**：`notebooks/phase-09-agent.ipynb` —— 输入自然语言请求并渲染 tool trace；断言工具调用序列符合预期、查询走本体接口、权限外操作被拒绝、工单在权限内创建成功。

## 六、里程碑与阶段依赖

| 里程碑 | 覆盖阶段 | 达成标志 |
| --- | --- | --- |
| M1 数据流打通 | 0 → 1 → 2 | 数据从 PG 自动进入 Kafka，链路可视 |
| M2 湖仓与服务化 | 3 → 4 → 5 | 一条数据可从 Kafka 落到 Iceberg，并被 StarRocks/OpenSearch 消费 |
| M3 本体抽象成立 | 6 | 统一对象 API 取代直连数据库 |
| M4 企业能力成立 | 7 → 8 | 权限差异可验证、Action 闭环可审计 |
| M5 智能入口成立 | 9 | Agent 端到端完成"查询-分析-操作" |

依赖关系为线性递进，但阶段 4、5 可在阶段 3 完成后并行；阶段 7 的权限模型可与阶段 8 并行设计。

每个里程碑的完成标准：对应阶段的验收 Notebook 全部绿灯（Restart & Run All 通过），并归档执行结果为 HTML。

## 九、环境与规模基线

| 项 | 基线 |
| --- | --- |
